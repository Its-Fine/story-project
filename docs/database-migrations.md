# Управление схемой PostgreSQL

Схемой Story Project управляет Flyway из `story-back`. Hibernate проверяет схему
через `ddl-auto=validate` и больше не создаёт и не изменяет таблицы автоматически.

Миграции находятся в `story-back/src/main/resources/db/migration`. Уже применённые
файлы нельзя редактировать: каждое следующее изменение схемы получает новый номер.
Команда `flyway clean` отключена.

## Новая пустая база

При первом запуске `story-back` Flyway применит V1–V5, после чего Hibernate
проверит соответствие JPA-сущностям. `story-auth` запускается только после того,
как `story-back` станет healthy.

## Существующая база без истории Flyway

Автоматический baseline выключен. Перед первой миграцией обязательно:

1. Остановить операции записи приложения, не удаляя контейнеры или volumes.
2. Сделать резервную копию и проверить, что файл дампа не пустой:

   ```powershell
   docker compose exec -T postgresql sh -lc 'pg_dump -Fc -U "$POSTGRES_USER" "$POSTGRES_DB"' > story-before-flyway.dump
   ```

3. Сравнить таблицы и обязательные столбцы с V1–V4. Для локальной базы это было
   выполнено 18 ноября 2026 года; для сервера проверку нужно повторить отдельно.
4. Только для одного проверенного запуска установить
   `STORY_FLYWAY_BASELINE_ON_MIGRATE=true` и пересоздать `story-back`.
   Flyway зарегистрирует существующую схему как baseline V1 и применит V2–V5.
5. Сразу вернуть `STORY_FLYWAY_BASELINE_ON_MIGRATE=false`, пересоздать сервис и
   убедиться, что повторный запуск не применяет миграции повторно.

Нельзя постоянно оставлять автоматический baseline включённым: он способен
замаскировать запуск приложения на неизвестной или неправильной базе.

## Проверка

История миграций:

```powershell
docker compose exec postgresql sh -lc 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "TABLE flyway_schema_history"'
```

В рабочем состоянии последняя успешная версия — V5, а оба backend-контейнера
имеют статус `Up`. Значения `installed_by` и учётные записи базы не следует
публиковать в отчётах или логах.

## Откат

Flyway Community не выполняет автоматические undo-миграции. Откат изменения
схемы выполняется восстановлением проверенной резервной копии в отдельную базу,
проверкой приложения и только затем согласованным переключением. Нельзя применять
`docker compose down -v` или удалять production volume.
