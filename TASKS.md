## T13. Административные статусы заявок и оценивание работ

**Проблема:** в БД уже существуют `applications.status`,
`applications.rejection_reason`, `works.rate` и `works.is_rated`, но действующие
admin-контроллеры предоставляют только чтение. Из-за этого frontend показывает
сообщение, что смена статуса и оценки пока не поддерживаются backend.

**Результат:** администратор может принять или отклонить заявку, указать понятную
причину отказа и выставить оценку работе. Участник видит актуальный статус,
причину отклонения и доступную ему итоговую оценку.

### Контракт и правила

- [x] Зафиксировать допустимые статусы как enum: `PENDING`, `ACCEPTED`, `REJECTED`;
  убрать произвольные строковые значения из сервисного слоя.
- [x] Разрешить администратору вернуть рассмотренную заявку в `PENDING` и изменить
  принятое решение; правила редактирования заявки участником пока не менять.
- [x] Зафиксировать диапазон оценки 0–100, возможность снять
  оценку и правило для повреждённых файлов.
- [x] Показывать оценку участнику сразу после выставления.
- [x] Использовать одну итоговую оценку на работу. Несколько оценок жюри остаются
  отдельной будущей задачей, поскольку требуют новой модели данных.

### Backend и API

- [x] Добавить DTO изменения статуса с полями `status` и `rejectionReason`;
  причина обязательна для `REJECTED` и очищается для других статусов.
- [x] Расширить `ResponseApplicationAdminDto` полями `status` и
  `rejectionReason`, чтобы административный интерфейс видел текущее решение.
- [x] Добавить административную операцию изменения статуса в существующее
  пространство `/api/v1/admin/applications/{appId}`. Предлагаемый вариант:
  `PATCH /api/v1/admin/applications/{appId}/status`.
- [x] Добавить DTO оценки и административную операцию в существующее пространство
  `/api/v1/admin/works/{workId}`. Предлагаемый вариант:
  `PUT /api/v1/admin/works/{workId}/rating`.
- [x] Расширить `ResponseWorkAdminDto` полями `rate` и `isRated`.
- [x] Возвращать `404` для отсутствующей заявки/работы, `400` для недопустимого
  статуса или оценки, `403` для пользователя без административного разрешения.
- [x] Проверять актуальные права администратора по БД, не доверяя только роли из JWT.
- [x] Выполнять изменение статуса и оценки транзакционно; предусмотреть защиту от
  одновременного редактирования двумя администраторами.
- [x] Добавить аудит решения: кто и когда изменил статус/оценку. Если для этого
  нужны новые столбцы, подготовить только аддитивную миграцию без потери данных.
- [x] До появления `story-admin` разместить реализацию в текущих admin-
  контроллерах `story-back`, но контракт должен переноситься в T04 без изменения
  внешнего API и без дублирования бизнес-логики.

- [x] Показывать статус и причину отклонения в списке заявок администратора.

### Проверки

- [x] Интеграционный тест правил статуса, обязательной причины отказа и диапазона оценок.
- [ ] Интеграционные тесты admin API для ADMIN, PARTICIPANT, banned и устаревшей роли.
- [ ] Проверка одновременного изменения одной заявки двумя запросами.
- [ ] Проверка сохранения решения после рестарта и отсутствия изменений файлов MinIO.
- [ ] Пользовательский сценарий frontend: принять, отклонить с причиной, оценить
  работу и увидеть результат в кабинете участника.

**Рекомендуемые коммиты:** отдельно модель/DTO/API статусов, отдельно API оценок,
отдельно административный frontend. Не смешивать эту задачу с Keycloak или
выделением `story-admin` в одном коммите.

## Правила выполнения каждой задачи

1. Сначала прочитать текущую реализацию и проверить локальные изменения пользователя.
2. Один небольшой логически завершённый шаг — один понятный коммит.
3. Добавить проверки поведения, особенно отрицательные сценарии безопасности.
4. Не восстанавливать удалённые устаревшие компоненты, не удалять данные и не
   выполнять `down -v`.
5. Сохранять совместимость либо явно описывать переход и обновление frontend.
6. В PR указывать: что изменено, какие тесты реально выполнены, ограничения,
   порядок развёртывания и отката. Незапущенные проверки не объявлять успешными.
7. После завершения обновить этот файл: статус, ссылка на коммит/PR, результаты.
8. Не считать «нет утечек» доказанным только разделением URL или скрытой кнопкой:
   проверять сервисы, сеть, разрешения, ownership, логи и доступ к хранилищам.
